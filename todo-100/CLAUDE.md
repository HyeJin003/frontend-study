## 컴포넌트 설계 기준

컴포넌트에 뭘 넣을지 모를 때 이 순서로 생각할 것:

  1. 이 컴포넌트가 화면에 그리는 게 뭔가?     → 그것만 보여주면 됨
  2. 그걸 그리는 데 필요한 데이터가 뭔가?     → 그것만 props/context로 받으면 됨
  3. 이 컴포넌트에서 일어나는 동작이 뭔가?    → 그 동작의 함수만 받으면 됨
  4. 필요 없는 건 절대 받지 않는다            → 안 쓰는 props는 넣지 말 것

예시:
  TodoItem   → todo 객체 + toggleTodo + deleteTodo + editTodo
  TodoEmpty  → filter (메시지만 보여주면 됨, todos 배열 전체 불필요)
  TodoFooter → activeCount + completedCount + filter + setFilter + clearCompleted

## 코드 작성 규칙

- TypeScript `any` 절대 금지 — 정확한 타입을 정의할 것
- 모든 "왜"를 주석으로 설명 — 무엇이 아닌 이유를 주석에 적을 것
- 새 번호 추가 시 이전 버전의 리팩토링 형태로 작성 (01 → 02 → 03 순서로 개선)

## 정답 파일 생성 규칙

todo-100 안에 새 정답 파일을 만들 때 반드시 상단 주석에 아래 고민 과정을 포함할 것:

```
// ── 이 파일을 설계할 때 한 고민 ────────────────────────────────
//
//   1. 화면에 뭘 보여줘야 하나?     → <실제 상태 목록>
//   2. 어떤 상태가 바뀌나?          → <변경 케이스>
//   3. 그 상태를 바꾸는 함수는?     → <함수 목록>
//   4. 타입을 어떻게 정의했나?      → <interface/type 설계 이유>
//   5. 자식 컴포넌트들이 뭘 필요로 하나? → <props/context value 결정 이유>
//
//   ── 면접 포인트 ──────────────────────────────────────────────
//   Q: "<예상 면접 질문>"
//   A: "<핵심 답변>"
```
