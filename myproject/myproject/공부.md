## 1. 전체 흐름

> "회원가입 버튼 눌렀을 때 무슨 일이 일어나나?"

```
[브라우저 폼]
  이메일, 비밀번호, 닉네임 입력 후 버튼 클릭
        ↓
  JSON으로 변환해서 서버로 전송
  { "email": "abc@gmail.com", "password": "1234", "nickname": "홍길동" }
        ↓
[Controller]
  요청 받아서 Service 호출만 함 (판단 X, 처리 X)
        ↓
[Service]
  실제 일 처리:
  1. 이메일 중복 확인
  2. 비밀번호 암호화
  3. Member 엔티티 조립
  4. DB 저장 (Repository한테 시킴)
  5. JWT 발급
        ↓
[Repository]
  DB에 저장/조회만 함
        ↓
[Service → Controller → 클라이언트]
  { "accessToken": "...", "refreshToken": "..." } 반환
```

### 각자 역할 한마디로
| 계층 | 역할 | 비유 |
|------|------|------|
| Controller | 요청 받고 넘기고, 응답 돌려주기 | 접수 창구 |
| Service | 실제 비즈니스 로직 처리 | 실무자 |
| Repository | DB 저장/조회만 | 서류 보관함 |

## 2. DTO vs Entity

### Entity
- DB 테이블과 1:1 매핑되는 클래스
- 모든 컬럼을 다 갖고 있음
- JPA가 이걸 보고 테이블 만들고 저장/조회

```java
// Member 엔티티 - DB의 모든 컬럼
id, email, password, nickname, providerId, role, provider, createdAt
```

### DTO (Data Transfer Object)
- API 통신 전용 봉투
- 필요한 것만 골라서 담음
- 상황마다 다르게 만듦

```java
// SignupRequestDto - 회원가입할 때 클라이언트가 보내는 것만
email, password, nickname  // 3개만!
```

### 왜 Entity 그대로 안 쓰나?
```
이유 1: 보안
  → 클라이언트가 { "role": "ADMIN" } 보내면?
  → Entity 그대로 받으면 누구든 관리자가 될 수 있음 (위험!)

이유 2: 응답에서 비밀번호 노출
  → Member 그대로 반환하면 password 필드도 나감 (위험!)

이유 3: 유연함
  → DB 구조 바뀌어도 API 스펙 유지 가능
  → API 스펙 바뀌어도 DB 구조 유지 가능
```

### 어디서 뭘 쓰나
```
클라이언트 → 서버: DTO 사용 (필요한 것만)
서버 → DB:        Entity 사용 (전체 구조)

Service에서 DTO + 서버가 결정한 값 → Entity 조립
```

## 3. Jackson

> "JSON 문자열을 Java 객체로 바꿔주는 라이브러리"

### 왜 필요하냐면
```
클라이언트가 보낸 JSON = 그냥 텍스트 덩어리
{ "email": "abc@gmail.com", "password": "1234" }

Java는 텍스트에서 .getEmail() 못 꺼냄
→ Java 객체로 변환해야 꺼낼 수 있음
```

### 변환 과정
```
JSON 문자열
{ "email": "abc@gmail.com", ... }
        ↓  Jackson 변환
1. @NoArgsConstructor로 빈 객체 먼저 만들기
2. email, password, nickname 하나씩 채워넣기
        ↓
SignupRequestDto 객체 완성
dto.getEmail() → "abc@gmail.com" 가능!
```

### 주의
```
@NoArgsConstructor 없으면 → Jackson이 빈 객체 못 만듦 → 변환 실패 → 에러!
```

## 4. Lombok 애노테이션

> "반복적으로 써야 하는 코드를 자동으로 만들어주는 라이브러리"

```java
@Getter
// 모든 필드의 getter 메서드 자동 생성
// getName(), getEmail() 등을 직접 안 써도 됨

@NoArgsConstructor
// 파라미터 없는 기본 생성자 자동 생성
// public Member() {}
// Jackson 역직렬화, JPA에서 필요

@AllArgsConstructor
// 모든 필드를 파라미터로 받는 생성자 자동 생성
// public Member(String email, String password, ...) {}
// @Builder가 내부적으로 사용

@Builder
// 골라서 넣는 방식으로 객체 만들 수 있게 해줌
// Member.builder().email("...").nickname("...").build()

@RequiredArgsConstructor
// final 필드만 파라미터로 받는 생성자 자동 생성
// Spring DI에서 사용
```

### Builder 세트로 달아야 하는 이유
```
@Builder            → builder() 패턴 사용 가능
@NoArgsConstructor  → JPA가 쓰는 기본 생성자
@AllArgsConstructor → @Builder가 쓰는 전체 생성자

@NoArgsConstructor만 달면 @Builder용 전체 생성자가 사라짐
→ 그래서 @AllArgsConstructor로 직접 만들어줘야 함
→ 세 개 세트!
```

## 5. Bean Validation

> "클라이언트가 보낸 값이 올바른지 자동으로 검사"

```java
@NotBlank
// null, "" (빈 문자열), " " (공백만) 전부 거부
// password, nickname에 사용

@Email
// 이메일 형식 검증
// "abc" → 거부, "abc@gmail.com" → 통과
// ※ 단독 사용 시 빈 문자열은 통과해버림!

// 그래서 email에는 둘 다 달아야 함
@NotBlank
@Email
private String email;
```

### 왜 프론트엔드에서 검사하는데 백엔드에서도 하나?
```
프론트 검증 = 브라우저 JavaScript로 실행
→ 개발자 도구로 JavaScript 비활성화 가능
→ Postman으로 검증 없이 서버에 직접 요청 가능
→ 5초면 우회 가능!

프론트 검증 → 사용자 편의용 (빠른 피드백)
백엔드 검증 → 진짜 방어선 (반드시 필요!)
```

### 검증이 실행되는 시점
```java
// Controller에서 @Valid 달아야 검증 실행됨!
public ResponseEntity<?> signup(@RequestBody @Valid SignupRequestDto dto)
// @Valid 없으면 @NotBlank, @Email 달아도 그냥 무시됨

// @Valid = "DTO에 붙은 검증 조건들 지금 실행해" 트리거
// DTO에 선언만 하면 실행 안 됨, Controller에서 @Valid로 발동시켜야 함
```

## 6. Spring Bean / DI

### Bean이란?
```
Spring이 직접 만들어서 창고에 보관하는 객체

@Service     붙은 클래스 → Spring이 Bean으로 관리
@Repository  붙은 클래스 → Spring이 Bean으로 관리
@Component   붙은 클래스 → Spring이 Bean으로 관리
@Configuration + @Bean → Spring이 Bean으로 관리
```

### DI (Dependency Injection, 의존성 주입)이란?
```
"필요한 객체를 Spring이 알아서 넣어줘"

// 내가 직접 만드는 방식 (나쁜 예)
MemberRepository repo = new MemberRepository(); // 직접 생성

// DI 방식 (좋은 예)
private final MemberRepository memberRepository;
// Spring이 창고에서 꺼내서 자동으로 넣어줌

비유:
요리사(Service)가 "냉장고(Repository) 필요해" 라고 선언만 하면
주방장(Spring)이 냉장고를 가져다 줌
요리사가 직접 냉장고 만들 필요 없음
```

### PasswordEncoder는 왜 직접 등록해야 하나?
```
@Service, @Repository → 구현체가 하나 → Spring이 알아서 만들어줌

PasswordEncoder → 인터페이스 (구현체가 여러 개)
  BCryptPasswordEncoder, Pbkdf2PasswordEncoder, SCryptPasswordEncoder...
  "어떤 거 써?" → Spring이 모름 → 우리가 직접 등록해야 함

@Configuration
public class SecurityConfig {
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder(); // 우리가 직접 선택
    }
}
```

## 7. Service 애노테이션 3형제

```java
@Service
// "Spring아, 이 클래스를 Bean으로 관리해줘"
// Controller가 AuthService 필요하다고 하면 Spring이 찾아서 넣어줌

@RequiredArgsConstructor
// final 필드들을 생성자로 자동 주입받게 해줌
// private final MemberRepository memberRepository;
// → Spring이 알아서 MemberRepository 넣어줌

@Transactional
// DB 작업을 하나의 묶음으로 처리
// 중간에 에러나면 전부 취소 (데이터 꼬임 방지)
// 예) Member 저장 성공 후 RefreshToken 저장 실패
//   → @Transactional 있으면 Member 저장도 같이 취소 → 안전
//   → @Transactional 없으면 Member만 저장된 채로 끝 → 데이터 꼬임
```

## 8. 인터페이스 vs 구현체

```
인터페이스 = 설계도 (규칙만 있음, 실제 로직 없음)
구현체     = 설계도 보고 실제로 만든 것 (로직 있음)

PasswordEncoder (인터페이스)
  → "encode() 메서드 있어야 해" 규칙만 정의

BCryptPasswordEncoder (구현체)
  → PasswordEncoder를 구현
  → 실제 BCrypt 암호화 로직 있음
```

### 왜 인터페이스를 타입으로 쓰나?
```java
// 구현체를 타입으로 쓰면
BCryptPasswordEncoder passwordEncoder = new BCryptPasswordEncoder();
// 나중에 암호화 방식 바꾸면 이 코드 찾아서 다 바꿔야 함

// 인터페이스를 타입으로 쓰면
PasswordEncoder passwordEncoder = new BCryptPasswordEncoder();
// 나중에 암호화 방식 바꿀 때 new 뒤에 구현체만 교체하면 됨 → 유연함
```

## 9. Builder 패턴

> "필드를 이름으로 골라서 넣는 객체 생성 방식"

### 왜 쓰나?
```java
// 일반 생성자 방식 (필드 많으면 헷갈림)
new Member("abc@gmail.com", "1234", "홍길동", null, Role.MEMBER, AuthProvider.NONE, null);
// 이게 뭔지 알 수가 없음...

// Builder 방식 (이름으로 넣으니까 한눈에 보임)
Member.builder()
    .email("abc@gmail.com")
    .password("1234")
    .nickname("홍길동")
    .role(Role.MEMBER)
    .provider(AuthProvider.NONE)
    .build();
```

### 사용하려면
```java
// 클래스에 @Builder 달아야 함
@Builder
@NoArgsConstructor   // 세트로!
@AllArgsConstructor  // 세트로!
public class Member { }

// 그러면 이렇게 쓸 수 있음
Member member = Member.builder()
    .email(dto.getEmail())
    .password(encodedPassword)
    .build();
```

## 10. Controller 계층

> "클라이언트 요청을 받아서 Service에 넘기고, 응답을 돌려주는 창구"

### Controller가 하는 일
```
1. URL 매핑 → 어떤 URL에 어떤 메서드를 연결할지
2. 요청 데이터 꺼내기 → @RequestBody, @RequestHeader 등
3. Service 호출
4. 응답 만들어서 반환
```

### Controller가 하면 안 되는 일
```
비즈니스 로직 (이메일 중복 확인, 비밀번호 암호화 등) → Service에서 해야 함
DB 직접 접근 → Repository에서 해야 함

Controller = 단순 중계자. 판단하지 않음.
```

### 기본 구조
```java
@RestController               // JSON 응답 자동 변환
@RequestMapping("/api/auth")  // 공통 URL 앞부분
@RequiredArgsConstructor      // Service 주입
public class AuthController {

    private final AuthService authService;

    @PostMapping("/signup")   // POST /api/auth/signup
    public ResponseEntity<ApiResponse<TokenResponseDto>> signup(
            @RequestBody @Valid SignupRequestDto dto) {

        TokenResponseDto token = authService.signup(dto);
        return ResponseEntity.ok(ApiResponse.success("회원가입 성공", token));
    }
}
```

### 애노테이션 정리
```
@RestController    = @Controller + @ResponseBody
                   → 모든 메서드 반환값을 JSON으로 자동 변환

@RequestMapping    = 공통 URL prefix. 클래스에 붙이면 모든 메서드에 적용

@PostMapping       = POST 요청 처리
@GetMapping        = GET 요청 처리
@PutMapping        = PUT 요청 처리
@DeleteMapping     = DELETE 요청 처리
```

## 11. ResponseEntity와 ApiResponse

### ResponseEntity란?
```
HTTP 응답 전체를 표현하는 객체
  → 상태 코드 (200, 404, 500...)
  → 헤더
  → 바디 (우리가 보내는 데이터)

ResponseEntity.ok(body)           → 200 OK + 바디
ResponseEntity.status(404).body() → 404 + 바디
```

### ApiResponse란?
```java
// 우리가 직접 만든 공통 응답 형태
{
    "success": true,
    "message": "회원가입 성공",
    "data": { "accessToken": "...", "refreshToken": "..." }
}

ApiResponse.success("회원가입 성공", token)  → 위 JSON 만들어줌
ApiResponse.fail("이메일 중복", null)        → success: false 형태
```

### 왜 ApiResponse로 감싸나?
```
감싸지 않으면 데이터만 나감:
{ "accessToken": "...", "refreshToken": "..." }

감싸면 성공 여부 + 메시지 + 데이터 묶음으로 나감:
{ "success": true, "message": "...", "data": { ... } }

프론트엔드에서 response.data.accessToken 으로 일관되게 꺼낼 수 있음
에러 응답도 같은 형식 → 프론트 처리 코드가 단순해짐
```

### 반환 타입 읽는 법
```java
ResponseEntity<ApiResponse<TokenResponseDto>>

바깥부터 읽기:
  ResponseEntity    → HTTP 응답 포장지
  ApiResponse       → 우리 공통 응답 형태
  TokenResponseDto  → 실제 데이터 (accessToken, refreshToken)
```

## 12. @RequestBody vs @RequestHeader

### @RequestBody
```java
@PostMapping("/signup")
public ResponseEntity<?> signup(@RequestBody SignupRequestDto dto)
```
```
요청의 Body(몸통)에서 데이터를 꺼내서 DTO에 담음

클라이언트가 이렇게 보냄:
POST /api/auth/signup
Content-Type: application/json

{ "email": "abc@gmail.com", "password": "1234", "nickname": "홍길동" }

→ Jackson이 JSON을 SignupRequestDto 객체로 변환해줌
→ dto.getEmail() 로 꺼낼 수 있음
```

### @RequestHeader
```java
@PostMapping("/logout")
public ResponseEntity<?> logout(@RequestHeader("Authorization") String bearerToken)
```
```
요청의 Header(헤더)에서 특정 값을 꺼냄

클라이언트가 이렇게 보냄:
POST /api/auth/logout
Authorization: Bearer eyJhbGciOi...

→ bearerToken = "Bearer eyJhbGciOi..."
→ bearerToken.substring(7) 로 "Bearer " 제거 → 순수 토큰만 추출
```

### 언제 뭘 쓰나?
```
회원가입, 로그인 → 폼 데이터를 Body에 담아 보냄 → @RequestBody
로그아웃, 내 정보 → 토큰을 Header에 담아 보냄  → @RequestHeader
```

## 13. extends vs implements

### extends (상속)
```java
public class OAuth2SuccessHandler extends SimpleUrlAuthenticationSuccessHandler
```
```
"부모 클래스를 물려받아서 확장해"

부모가 이미 구현된 기능들을 제공해줌
필요한 메서드만 @Override 해서 덮어씌움
나머지는 부모 것 그대로 사용

class A extends B → A는 B의 기능을 물려받음
```

### implements (구현)
```java
public class GoogleOAuth2UserInfo implements OAuth2UserInfo
```
```
"인터페이스의 규칙을 지켜서 만들어"

인터페이스 = 규칙만 있음 (메서드 목록)
implements 하면 그 규칙에 적힌 모든 메서드를 반드시 만들어야 함

interface OAuth2UserInfo {
    String getEmail();    // 규칙: 이런 메서드 있어야 함
    String getNickname();
}

class GoogleOAuth2UserInfo implements OAuth2UserInfo {
    // 반드시 getEmail(), getNickname() 구현해야 함
}
```

### 차이점 한눈에
```
extends   → 부모의 기능을 물려받음. 부모가 이미 코드 있음.
implements → 인터페이스의 규칙을 따름. 내가 직접 코드 작성.

extends   → 클래스 하나만 상속 가능
implements → 인터페이스 여러 개 동시에 구현 가능
```

### @Override
```java
@Override
public String getEmail() {
    return (String) attributes.get("email");
}
```
```
"부모(또는 인터페이스)에서 정의한 메서드를 내가 새로 작성할게"

없어도 동작은 함
있으면 컴파일러가 "이게 진짜 오버라이드인지" 검사해줌
오타 났을 때 에러로 잡아줌 → 달아두는 게 좋음
```

### abstract (추상)
```java
public abstract class OncePerRequestFilter {
    protected abstract void doFilterInternal(...);  // 자식이 채워야 함
}
```
```
abstract 메서드 = 내용 없이 이름만 선언된 메서드
"자식 클래스가 반드시 구현해야 해" 라는 강제 규칙

abstract 클래스 = 일부는 구현됐고, 일부는 자식한테 맡긴 클래스
직접 new로 객체 만들 수 없음 → 반드시 extends해서 사용
```

### protected가 뭐야?
```
접근 제어자 종류:
  public    → 어디서든 접근 가능
  protected → 같은 패키지 + 자식 클래스에서만 접근 가능
  private   → 해당 클래스 안에서만 접근 가능

doFilterInternal이 protected인 이유:
  → 외부에서 직접 호출하는 메서드가 아님
  → OncePerRequestFilter 부모가 내부적으로 호출함
  → 자식(JwtAuthenticationFilter)만 오버라이드할 수 있게
```

## 14. JWT (JSON Web Token)

> "로그인하면 서버가 발급하는 암호화된 통행증"

### AccessToken vs RefreshToken
```
AccessToken  (1시간)  → 실제 API 호출에 사용
RefreshToken (7일)   → AccessToken 만료 시 재발급용

로그인 → 둘 다 발급
1시간 후 AccessToken 만료 → RefreshToken으로 /refresh 요청 → 새 AccessToken 발급
7일 후 RefreshToken도 만료 → 다시 로그인
```

### 왜 매 요청마다 아이디/비번 안 보내나?
```
비밀번호를 계속 보내면:
1. 네트워크에 비밀번호가 계속 노출 → 탈취 위험
2. BCrypt 비교가 의도적으로 느림 → 서버 성능 저하
3. 사용자가 매번 비밀번호 입력 불가능

그래서 토큰 = 짧게 살고, 탈취돼도 피해 최소화
```

### 토큰에 뭘 담나?
```
AccessToken  → 이메일 + 권한(role)  (API마다 누구인지, 뭘 할 수 있는지 필요)
RefreshToken → 이메일만            (재발급용이라 권한 필요 없음)

비밀번호는 절대 넣으면 안 됨 → 토큰은 디코딩하면 내용이 보임!
```

### 왜 브라우저 닫아도 로그인 유지되나?
```
서버가 기억하는 게 아님!
브라우저(클라이언트)가 토큰을 localStorage나 쿠키에 저장해둠
브라우저 닫아도 저장소에 남아있음 → 다시 열면 토큰 그대로 사용

서버는 무상태(stateless) → 이전 요청 기억 못 함 → 매번 토큰으로 확인
```

## 15. AuthService 메서드 4개

### signup
```
1. 이메일 중복 확인 (existsByEmail)
2. 비밀번호 암호화 (passwordEncoder.encode)
3. Member 엔티티 만들기 (builder)
4. DB 저장 (memberRepository.save)
5. AccessToken + RefreshToken 발급
6. RefreshToken DB 저장
7. TokenResponseDto 반환
```

### login
```
1. 이메일로 Member 조회 (findByEmail → orElseThrow)
2. 비밀번호 확인 (passwordEncoder.matches)
3. AccessToken + RefreshToken 발급
4. 기존 RefreshToken 삭제 후 새로 저장 (deleteByMember → save)
5. TokenResponseDto 반환

※ signup과 다른 점:
   - 이메일 중복 확인 대신 Member 조회
   - 비밀번호 암호화 대신 비밀번호 비교 (matches)
   - 기존 RefreshToken 먼저 삭제 (이미 로그인한 적 있을 수 있으니까)
```

### refresh
```
1. 토큰 유효성 검증 (validateToken) → 형식 + 만료 확인
2. DB에 있는 토큰인지 확인 (findByToken) → 위조/로그아웃 여부 확인
3. 토큰에서 이메일 꺼내기 (getEmail)
4. 이메일로 Member 조회
5. 새 AccessToken 발급해서 반환 (String 반환)
```

### logout
```
1. 토큰에서 이메일 꺼내기 (getEmail)
2. 이메일로 Member 조회
3. RefreshToken DB에서 삭제 (deleteByMember)
   → 삭제하면 이후 refresh 요청해도 DB에 없으니까 거부됨
```

### me
```
1. 토큰에서 이메일 꺼내기 (getEmail)
2. 이메일로 Member 조회 후 반환
```

## 17. OncePerRequestFilter

> "요청 하나당 딱 한 번만 실행되는 필터 기반 클래스"

### 왜 OncePerRequestFilter를 상속하나?
```
Spring에서 필터가 한 요청에서 여러 번 실행될 수 있는 경우가 있음
(forward, include 등으로 내부 재요청 발생 시)

OncePerRequestFilter = "이미 실행됐으면 두 번 실행 안 해"
JWT 검사 같은 건 한 번만 하면 됨 → OncePerRequestFilter 사용
```

### 구조
```java
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain filterChain) throws ServletException, IOException {

        // 여기에 JWT 검증 로직 작성
        // 마지막엔 반드시 다음 필터로 넘겨야 함
        filterChain.doFilter(request, response);
    }
}
```

### FilterChain이 뭐야?
```
필터들이 줄 서있는 체인
filterChain.doFilter(request, response) = "다음 필터로 넘겨"

이걸 안 호출하면 요청이 거기서 멈춤 → 컨트롤러까지 못 감
JWT 검증 실패해도 일단 넘기는 이유:
  → 허용된 URL(/signup, /login)은 필터 통과해야 하니까
  → 인가(권한 체크)는 Security가 나중에 따로 함
```

## 18. JwtAuthenticationFilter 흐름

> "모든 요청이 컨트롤러 도달 전에 통과하는 JWT 검사관"

```
요청 들어옴
  ↓
1. Authorization 헤더 있어?
   없으면 → 그냥 통과 (로그인 안 필요한 URL일 수 있으니까)
  ↓
2. "Bearer "로 시작해?
   아니면 → 그냥 통과
  ↓
3. "Bearer " 제거 → 순수 토큰 추출
  ↓
4. 토큰 유효한지 검사 (validateToken)
   유효 안 하면 → 그냥 통과 (다음 필터에서 401 처리)
  ↓
5. 토큰에서 이메일 꺼내기 (getEmail)
  ↓
6. SecurityContextHolder에 인증 정보 등록
   → 이후 컨트롤러에서 "이 사람 로그인된 사람"으로 인식
  ↓
7. 다음 필터로 넘기기
```

### SecurityContextHolder가 뭐야?
```
로그인된 사용자 정보를 요청 처리 동안 임시로 보관하는 곳
JWT 필터에서 등록해두면 → 이후 컨트롤러까지 "이 사람 인증됨" 상태로 유지
요청 끝나면 자동으로 비워짐 (다음 요청에 영향 없음)
```

## 19. Spring Security - SecurityConfig

> "모든 HTTP 요청이 컨트롤러 도달 전에 통과하는 보안 설정"

### 전체 구조
```java
@Configuration
@RequiredArgsConstructor
public class SecurityConfig {

    private final JwtAuthenticationFilter jwtAuthenticationFilter;
    private final CustomOAuth2UserService customOAuth2UserService;
    private final OAuth2SuccessHandler oAuth2SuccessHandler;
    private final OAuth2FailureHandler oAuth2FailureHandler;

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())
            .sessionManagement(session ->
                session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/signup", "/api/auth/login", ...).permitAll()
                .anyRequest().authenticated()
            )
            .oauth2Login(oauth2 -> oauth2
                .userInfoEndpoint(userInfo -> userInfo.userService(customOAuth2UserService))
                .successHandler(oAuth2SuccessHandler)
                .failureHandler(oAuth2FailureHandler)
            )
            .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}
```

### .csrf(csrf -> csrf.disable())
```
CSRF = 나쁜 사람이 다른 사이트에서 몰래 우리 서버에 요청 보내는 공격

이 공격이 성립하려면 브라우저가 쿠키를 자동으로 실어보내야 함
우리는 쿠키 안 씀 → JWT 토큰을 헤더에 직접 담아서 보냄
브라우저는 헤더를 자동으로 보내지 않음 → 공격 자체가 안 됨 → 꺼도 됨
```

### .sessionManagement(...STATELESS)
```
세션 = 로그인하면 서버가 "이 사람 로그인 중"이라고 서버 메모리에 저장하는 것

JWT는 토큰 안에 이미 "나 누구" 정보가 들어있음
서버가 따로 기억 안 해도 토큰만 보면 알 수 있음

STATELESS = "서버야, 기억하지 마"
안 하면 Spring Security가 기본으로 세션을 만들려 함 → 불필요한 메모리 낭비
```

### .authorizeHttpRequests(auth -> auth ...)
```
"이 URL은 누구나 와도 되고, 저 URL은 토큰 있어야 해" 규칙

.requestMatchers(...).permitAll()
→ 회원가입/로그인은 토큰이 아직 없는 상태에서 오는 요청 → 열어야 함
→ /oauth2/**, /login/oauth2/** 는 소셜 로그인 흐름에서 Spring이 내부적으로 쓰는 경로

.anyRequest().authenticated()
→ 나머지 전부 토큰 없으면 401 에러
→ 덕분에 컨트롤러마다 "로그인했어?" 체크 코드 안 써도 됨
```

### .oauth2Login(oauth2 -> oauth2 ...)
```
소셜 로그인 담당자 3명 지정

.userInfoEndpoint → userService(customOAuth2UserService)
  → 소셜 로그인 성공 후 사용자 정보 처리, DB 저장

.successHandler(oAuth2SuccessHandler)
  → 모든 처리 끝난 후 JWT 발급해서 응답

.failureHandler(oAuth2FailureHandler)
  → 소셜 로그인 중 실패하면 에러 응답
```

### .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)
```
Spring Security 안에는 여러 필터가 순서대로 줄 서있음
addFilterBefore = "이 필터 앞에 끼워넣어"
→ JWT 필터가 먼저 실행됨 → 모든 요청이 JWT 검사를 먼저 받음
```

### return http.build()
```
위에서 설정만 쌓은 상태 = 설계도
.build() 호출 → 실제로 동작하는 SecurityFilterChain 객체 완성
return 하면 Spring이 받아서 모든 요청에 적용
```

### Spring이 자동으로 해주는 것

## 21. OAuth2 구현 클래스들

### CustomOAuth2UserService
```java
@Service
public class CustomOAuth2UserService extends DefaultOAuth2UserService {

    @Override
    public OAuth2User loadUser(OAuth2UserRequest userRequest) {
        // 1. 부모가 구글/카카오에서 사용자 정보 가져옴
        OAuth2User oAuth2User = super.loadUser(userRequest);

        // 2. 어떤 소셜인지 확인 (google / kakao / naver)
        String registrationId = userRequest.getClientRegistration().getRegistrationId();

        // 3. 소셜마다 데이터 구조가 달라서 각각 다르게 꺼냄
        OAuth2UserInfo userInfo;
        if (registrationId.equals("google")) {
            userInfo = new GoogleOAuth2UserInfo(oAuth2User.getAttributes());
        } else if (registrationId.equals("kakao")) {
            userInfo = new KakaoOAuth2UserInfo(oAuth2User.getAttributes());
        } else {
            userInfo = new NaverOAuth2UserInfo(oAuth2User.getAttributes());
        }

        // 4. DB 조회 → 없으면 신규 회원 저장
        Member member = memberRepository.findByEmail(userInfo.getEmail()).orElse(null);
        if (member == null) {
            member = Member.builder()
                .email(userInfo.getEmail())
                .nickname(userInfo.getNickname())
                .password(null)          // 소셜 로그인은 비밀번호 없음
                .role(Member.Role.MEMBER)
                .provider(Member.AuthProvider.valueOf(registrationId.toUpperCase()))
                .build();
            memberRepository.save(member);
        }

        return oAuth2User;
    }
}
```

### OAuth2SuccessHandler
```java
@Component
public class OAuth2SuccessHandler extends SimpleUrlAuthenticationSuccessHandler {

    @Override
    public void onAuthenticationSuccess(...) throws IOException {
        String email = authentication.getName();  // 로그인한 사람 이메일

        Member member = memberRepository.findByEmail(email).orElseThrow();

        String accessToken = jwtProvider.generateAccessToken(member.getEmail(), member.getRole().name());
        String refreshToken = jwtProvider.generateRefreshToken(member.getEmail());

        // JSON으로 토큰 응답
        response.setContentType("application/json");
        response.getWriter().write("{\"accessToken\":\"" + accessToken + "\",\"refreshToken\":\"" + refreshToken + "\"}");
    }
}
```

### OAuth2FailureHandler
```java
@Component
public class OAuth2FailureHandler extends SimpleUrlAuthenticationFailureHandler {

    @Override
    public void onAuthenticationFailure(...) throws IOException {
        response.setStatus(HttpServletResponse.SC_BAD_REQUEST);  // 400
        response.setContentType("application/json");
        response.getWriter().write("{\"message\":\"소셜 로그인 실패\"}");
    }
}
```

### 전체 소셜 로그인 흐름
```
1. 사용자가 /oauth2/authorization/google 클릭
2. Spring이 자동으로 구글 로그인 페이지로 redirect
3. 사용자 구글 로그인
4. 구글이 /login/oauth2/code/google 로 code 전달
5. Spring이 code로 이메일/이름 등 사용자 정보 가져옴 (자동)
6. CustomOAuth2UserService.loadUser() 실행 → DB 저장
7. OAuth2SuccessHandler.onAuthenticationSuccess() 실행 → JWT 발급
8. 클라이언트에 accessToken, refreshToken 응답
```

## 22. 헷갈렸던 것들 Q&A

### Q. 로그인할 때 왜 반환값이 필요해? 확인만 하면 되는 거 아니야?
```
서버는 무상태(stateless) → 이전 요청을 기억 못 함
로그인 성공했다는 사실을 서버가 저장하지 않음

그러면 다음 API 요청할 때 "나 로그인한 사람이야"를 어떻게 증명해?
→ 로그인 성공 시 토큰을 클라이언트에게 줘야 함
→ 클라이언트가 토큰을 저장해뒀다가 매 요청마다 들고 옴

토큰을 안 돌려주면 클라이언트가 저장을 못 해서
이후 모든 API에서 본인 증명 불가능
```

### Q. refresh 메서드에서 왜 또 토큰 검증해? 로그인할 때 이미 했잖아
```
refresh는 로그인이랑 완전히 별개의 요청임

예) 1월 1일 로그인 → 토큰 발급
    1월 1일 1시간 후 → AccessToken 만료
    클라이언트가 /refresh 로 RefreshToken 보냄
    → 이게 refresh 메서드 실행 시점

서버는 무상태 → 1시간 전 로그인 기억 못 함
그래서 RefreshToken 받을 때마다 새로 확인:
  1. 형식이 올바른 토큰이야? (만료/위조 검사)
  2. DB에 있는 토큰이야? (로그아웃했거나 위조된 거 걸러내기)
```

### Q. login할 때 왜 기존 RefreshToken 지우고 새로 저장해?
```
login = 이미 가입된 회원이 다시 로그인하는 것
→ DB에 이전 RefreshToken이 남아있을 수 있음

예) 1월 1일 로그인 → RefreshToken A 저장
    1월 3일 로그아웃 안 하고 다시 로그인 → RefreshToken B 저장
    → DB에 A, B 두 개 → 한 회원에 토큰이 여러 개 (문제!)

그래서 로그인할 때:
  1. 기존 RefreshToken 삭제 (deleteByMember)
  2. 새 RefreshToken 저장 (save)
  → 항상 최신 토큰 하나만 유지
```

### Q. refresh 반환이 왜 String이야? TokenResponseDto 아니야?
```
refresh = AccessToken 하나만 새로 발급
RefreshToken은 그대로 유지 (아직 유효하니까)

TokenResponseDto = accessToken + refreshToken 두 개 묶음
→ 하나만 줄 때 쓰기엔 과함

String accessToken = "새로 만든 토큰"
→ 그냥 String으로 반환이 더 자연스러움
```

### Q. logout이랑 me 어떻게 달라?
```
logout
  반환 타입 void → 돌려줄 게 없음
  1. 토큰에서 이메일 꺼내기
  2. 이메일로 Member 조회
  3. RefreshToken DB 삭제 → 이후 refresh 요청 거부됨 = 강제 만료

me
  반환 타입 Member → 내 정보를 돌려줘야 함
  1. 토큰에서 이메일 꺼내기
  2. 이메일로 Member 조회
  3. return member

둘 다 흐름은 같은데 logout은 삭제, me는 조회 후 반환이 목적
```

### Q. @Valid가 뭐야? DTO에서 이미 검증 선언한 거 아냐?
```
@NotBlank, @Email = DTO에 선언만 해둔 것 = 규칙 목록

@Valid = "지금 이 규칙들 검사해" 실행 트리거

@Valid 없으면 규칙은 있지만 아무도 검사 안 함
Controller에서 @Valid를 달아야 실제로 검증이 실행됨
```
